# 蒸馏与更新

## 1. 确认可读范围

记录实际拿到的材料、版本及章节。目录仅用于覆盖地图。遇到截断、扫描模糊、缺页时标出，不从模型记忆补成原书。用户只有部分章节也可做局部蒸馏，明确局部状态。

## 2. 建立覆盖地图

先浏览可读结构，按章节或自然论证分段。识别问题、主张、概念、方法和边界，再以可独立调用的单元重组。允许跨章合并，但保留对应章节关系。

长书逐批处理：每批读取实际正文 → 生成/修订单元 → 更新索引和进度。不要先声称读完再分批补内容。恢复时先读 PROGRESS、INDEX 与相关既有单元，从待处理位置继续。

## 3. 写知识单元

遵循 unit.md。先确保情境、条件和方法的联系，再补证据与反例；原文缺项就留下缺口。把推断的适用条件标为待验证，避免推断在后续调用中成为硬事实。

将作者立场写成具体取舍，例如「更重视稳定而非增长速度」，而非笼统赞美。把概念写清定义及区别，把原则写为可影响选择的约束。不将“作者建议”写成“已被证明”。

## 4. 合并、关系与跨书冲突

先读既有索引检索相似单元，查看全文后决定保留、补充或拆分。比较问题、目标、前提和机制，不只比较标题。多来源支持相同主张时保留各自证据边界。

遇到冲突，区分：定义不同、适用情境不同、目标不同、时间范围不同、证据不一致、直接逻辑矛盾。条件不明时保留未解决状态。不要按知名度、出版时间或数量自动判胜。

## 5. 验收并交付

逐段核对覆盖地图，确保独特且影响决策的信息均有去向。检查关系 ID、索引路径与文件真实存在。按 unit.md 的三种情境抽查主要方法；有问题就修订后再交付。

汇报实际覆盖范围、单元数量、关键未知项、未处理位置。若完整材料已读完且覆盖核对通过，才能标「本次提供材料处理完成」。不得把“该摘录处理完成”扩大为“全书完成”。

不自动联网补充。用户明确要求外部验证时，使用可用搜索能力并将外部信息与书内信息分开；不能联网就记录验证未完成。
